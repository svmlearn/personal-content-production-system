# 作品集真实项目入口与小红书平台 UI 重塑 PRD

状态：执行版草案 v0.2
日期：2026-05-28

## 1. 背景

当前个人网站已经完成作品集首页与项目详情层，但“小红书抖音矩阵获客平台”不是普通展示项目，而是一个真实可运行的系统。

用户希望作品集不是只讲经历，而是在关键项目上能进入真实产品环境。尤其是小红书平台，后续部署到云服务器后，应允许访问者从作品集详情页点击“启动项目”进入真实系统。

这里的“启动项目”不是点击按钮后临时启动服务，而是：

1. 作品集服务长期运行。
2. 小红书平台服务长期运行。
3. 作品集按钮跳转到小红书平台的访问地址。

## 2. 当前技术事实

当前个人网站是静态页面：

- `apps/portfolio/index.html`
- `apps/portfolio/styles.css`
- `apps/portfolio/script.js`

它可以直接用浏览器打开，也可以作为静态资源放到任意 Web 服务里。

### 2.2 小红书平台现状

本地参考项目位置：

- `refrences/小红书抖音矩阵获客平台`

正式主应用位置：

- `apps/content-growth-platform`

- `refrences/小红书抖音矩阵获客平台/app`

技术栈：

- Next.js `16.2.4`

- TypeScript
- Tailwind CSS v4
- lucide-react
- shadcn / Base UI 组件体系

## 3. 产品目标

### 3.1 第一目标

让个人作品集从“展示项目”升级为“进入真实项目的入口”。

访问者在小红书项目详情页看到：

- 项目文字介绍
- 关键能力拆解
- 项目截图或产品画面
- “启动项目 / 进入真实系统”按钮

点击按钮后进入已运行的小红书平台。

### 3.2 第二目标

将个人网站改造成与小红书平台更一致的 Web 技术栈，降低未来同服务器部署、路由跳转、组件复用和维护成本。

建议目标栈：

- Next.js
- React
- TypeScript
- Tailwind CSS
- lucide-react

是否完全跟随小红书平台的 Next.js / React 版本，可在迁移时按兼容性确认。原则是：作品集项目独立，不把小红书业务代码搬进作品集。

### 3.3 第三目标

对小红书平台做 UI 风格重塑，但不改业务技术栈、不重写底层链路。

重塑目标不是“炫”，而是让它更像一个面向商家的 AI 营销内容操作系统。

## 4. 非目标

本阶段不做：

1. 不修改小红书平台的业务链路。
2. 不替换小红书平台的技术栈。
3. 不把小红书平台代码合并进个人网站。
4. 不在浏览器按钮里执行服务器启动命令。
5. 不解决最终线上账号、支付、正式域名、ICP备案等运营事项。

## 5. 部署理解

### 5.1 本地运行方式

本地可以同时启动两个服务：

1. 作品集 Next.js 项目：例如 `http://localhost:3000`
2. 小红书平台 Next.js 项目：例如 `http://localhost:3001`

小红书平台本地启动建议：

```bash
cd apps/content-growth-platform
pnpm install
cp .env.example .env.local
pnpm dev --port 3001
```

注意：小红书平台依赖 PostgreSQL、对象存储、AI runtime、Dify、worker secret 等环境变量。只看入口页可能不需要完整配置；要跑通咨询、内容生成、素材、视频链路，需要按 `.env.example` 补齐运行环境。

当前静态作品集里的“进入该项目”按钮由 `apps/portfolio/script.js` 按访问环境生成地址：

1. 本地静态预览时跳转到 `http://localhost:3001/login?demo=1&next=%2Fdashboard`。
2. 服务器 IP / 域名访问时，按同一 host 的 `3001` 端口生成内容平台地址。
3. 如果后续把作品集重写为 Next.js，再改为从 `NEXT_PUBLIC_JINGJING_URL` 读取可配置入口。

### 5.2 服务器运行方式

后续租一台 2 核 4G 云服务器时，可以在同一台服务器上同时跑：

1. 个人作品集服务
2. 小红书平台服务
3. PostgreSQL
4. content-generation worker
5. video-worker 及其依赖服务
6. Nginx / Caddy 作为反向代理

推荐先用同一台服务器部署，原因是：

- 成本低
- 管理简单
- 项目之间只是跳转，不需要强耦合
- 作品集和小红书平台可以分别重启、分别升级

### 5.3 访问地址方案

#### 方案 A：IP + 端口

示例：

- 作品集：`http://86.12.x.x:3000`
- 小红书平台：`http://86.12.x.x:3001`

优点：

- 最快
- 不依赖域名
- 适合早期验证

缺点：

- 不够正式
- 端口暴露较多
- 分享给别人时显得像测试环境

#### 方案 B：同 IP + 反向代理路径

示例：

- 作品集：`http://86.12.x.x/`
- 小红书平台：`http://86.12.x.x/jingjing`

优点：

- 只有一个入口
- 不需要域名

缺点：

- Next.js 项目如果不是按子路径部署，可能要配置 `basePath`、静态资源路径和反向代理规则。
- 对现有小红书项目侵入更大，不作为首选。

#### 方案 C：域名 / 子域名

示例：

- 作品集：`https://yang.example.com`
- 小红书平台：`https://jingjing.example.com`

优点：

- 最正式
- 不需要暴露端口
- 两个项目边界清晰

缺点：

- 需要 DNS、HTTPS 证书和反向代理配置
- 如果使用中国大陆服务器并对外提供互联网信息服务，通常需要按工信部备案要求处理

本项目推荐路径：

1. 本地先用 `localhost:3000` + `localhost:3001`
2. 服务器早期用 IP + 端口验证
3. 稳定后用海外服务器 + 域名 / 子域名

## 7. 小红书平台 UI 重塑需求

### 7.1 当前问题

当前小红书平台入口风格偏黑金，像一个通用后台或内部管理系统。它能用，但不够贴合“AI 营销内容操作系统”的产品心智。

### 7.2 目标风格

新的 UI 方向：

- 商家内容增长工作台
- AI 营销操作系统
- 清爽、可信、可长期使用
- 有一点科技感，但不是重暗黑
- 有内容日历、素材、脚本、任务流的“生产调度感”

建议避免：

- 大面积黑金
- 太像加密货币 / 金融后台
- 过度装饰化的科技大屏
- 只靠渐变和发光表达 AI

### 7.3 视觉关键词

建议关键词：

- 内容作战台
- 营销日历
- 素材流
- AI 策略顾问
- 品牌增长
- 任务队列
- 图文 / 视频生产流水线

### 7.4 色彩方向

建议基调：

- 主背景：浅灰白、暖白或低饱和浅色
- 主文字：深灰黑
- 小红书相关提示色：红、玫红、珊瑚色，但不直接复制小红书官方品牌
- AI / 系统状态提示色：青绿、蓝绿或电光蓝作为辅助
- 成功 / 运行状态：绿色
- 警告 / 待处理：橙色

可参考方向：

```txt
背景：#F7F7F4 / #FAFAF7
主文字：#1F2328
品牌强调：#F2556B / #E94B73
AI 辅助：#22B8A7 / #46A6FF
边框：rgba(31, 35, 40, 0.10)
```

### 7.5 页面优先级

第一批改 UI 的页面：

1. 首页入口页：`src/app/page.tsx`
2. 用户登录后主工作台：`src/app/dashboard/page.tsx`
3. 咨询诊断：`src/components/merchant/consultation-workspace.tsx`
4. 营销日历 / 每日任务：`src/components/merchant/daily-tasks-workspace.tsx`
5. 图文工作台：`src/components/merchant/article-workbench.tsx`
6. 视频工作台：`src/components/merchant/video-workbench.tsx`
7. 素材中心：`src/components/merchant/content-center.tsx`

改造原则：

- Stage 0 只改视觉表达、容器、色彩、边框、阴影、圆角和外壳氛围，不改信息层级和模块命名。
- Stage 1 如需改页面布局、信息层级或模块命名，必须另写任务书并先确认。
- 不改接口契约。
- 不改数据库结构。
- 不改 worker 调度。
- 不改现有业务状态机。
